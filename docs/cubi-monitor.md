# Generic Xianyu monitor CLI

This fork retains upstream Web/API code, but the `src.cubi_monitor` mode is independent. It runs no Web server, exports no cookie state and does not use the upstream scraper's skip-old-ID pipeline. Required runtime dependencies are Python 3.11+ and existing Playwright; JSON parsing and keyword normalization reuse upstream pure modules. A host Reader adapter provides one owned background CDP target and closes only that target. No new external dependencies were added.

Copy [the synthetic two-category example](../examples/monitor.example.json) to an owner-private location, replace example endpoints/baselines, and keep it out of Git. Price ceilings, exclusions, preferences and comparison references belong to each task's `criteria`/`baseline_refs`. References are dated observed/negotiated claims, not proof of sale or hardware health. Model image URLs are not downloaded: text-only analysis always reports pictures unchecked.

```
python3 -m src.cubi_monitor.cli --config PRIVATE_CONFIG --database PRIVATE_DB register
python3 -m src.cubi_monitor.cli --config PRIVATE_CONFIG --database PRIVATE_DB --monitor TASK scan --prepare
python3 -m src.cubi_monitor.cli --config PRIVATE_CONFIG --database PRIVATE_DB --monitor TASK activate
python3 -m src.cubi_monitor.cli --config PRIVATE_CONFIG --database PRIVATE_DB run
python3 -m src.cubi_monitor.cli --config PRIVATE_CONFIG --database PRIVATE_DB --monitor TASK status
python3 -m src.cubi_monitor.cli --config PRIVATE_CONFIG --database PRIVATE_DB --monitor TASK stop
python3 -m src.cubi_monitor.cli --config PRIVATE_CONFIG --database PRIVATE_DB --monitor TASK resume
```

`register` is not activation. `activate` creates one immutable expiry; restart/config changes cannot extend it. Prepare reads are explicitly requested, consume their own bounded analysis allocation, and do not advance live cadence/health/expiry or send recommendations. `run` processes configured tasks sequentially under one database file lock. New tasks quietly establish the initial baseline by default. Daily scheduling is the host's job; one persistent timer catch-up does not replay every missed day. Disabled/stopped/expired tasks perform no collection or AI.

Search defaults to **one page per keyword per sort**, both native new-publish and new-price sorts on every round, with overlapping three-day publish windows. `search_policy.sorts` can select one or both sorts; `publish_window` selects the native publish window. `scan_budget.total_pages` (default 12) caps the entire task, not each keyword; keywords rotate when that budget truncates coverage. Every seventh successful round (`sweep_every`, 0 disables), only the first rotating keyword gets a two-page latest sweep, sharing the same total cap. Coverage records omitted searches and shortened page budgets. Explicit old `pages: 2` remains supported. ID identifies a listing; dates restrict search coverage only. A first discovery is not proof of a new publication. This is not full-market coverage, nor proof that the seller has not deleted/reposted an item under another ID.

Facts are shared in `(platform,item_id)` items; task relationships store separate decisions, manual quotes and watches. Observations retain source and price. Assessments bind item fingerprint, semantic criteria/baseline hash and evaluator version; browsing counts/relative times/thumbnail changes do not trigger AI. Meaningful price changes compare against last assessment, with task-configured fraction or crossing its hard maximum **or the first matching rule's target ceiling**. Partial lists preserve detailed facts and unknown price never becomes zero. A rotating watch refresh and changed/configured-group/unknown queue lanes share bounded detail/analysis allocations. Rules' optional `group` labels reserve category opportunities; an unknown lane gets periodic priority. Queue selection returns SQL-limited rows, and cheap triage uses 100-row keyset batches with a per-round `triage_items` cap (default 500) and a persisted rotating cursor. Stored observations and historical assessments are never fed wholesale to AI. After detail capture, an exact already-assessed snapshot skips AI even if a list price had suggested a change. AI failure retains pending status and consumes a run's call allocation; there is no automatic unlimited retry.

Rules and hard exclusions accept `fields` (title/description, default both) and `exclude_pattern` to avoid incidental mentions. Rule regexes and budgets validate before capture. Product semantics live only in private criteria: the core contains no computer/GPU model names. Optional `criteria.defer_below_price` defers unknown or placeholder prices rather than rejecting the listing or consuming AI; `awaiting_price` is separate from the active queue, and a newly observed effective price reopens it. If the seller never updates that price, automatic monitoring cannot discover a private quote. Criteria changes invalidate old judgments; an unchanged scan policy does not. Existing new/unassessed rows stay new after a criteria change.

`notification_policy.watch_price_changes` defaults true. During live scans, meaningful decreases on explicit watch items can enqueue a price-change notice without waiting for AI, including an otherwise reserved item. A notice is not a purchase recommendation; it retains the independent negotiated quote. Changes are deduplicated in the existing outbox, with stale price/criteria or hard exclusions suppressed. Prepare, initial quiet baselines, inactive tasks and stopped/expired tasks cannot generate these notices. Candidate notices distinguish first discovery, price decrease and updated facts, without claiming every first discovery is newly published. Weekly summaries include active/deferred queue counts and coverage truncation. No additional database schema, deleted history or renewed expiry is needed.

If global `networkidle` times out during navigation, this adapter accepts completion only when the current owned page has a valid matching item/search API response and passes the same login/challenge boundary checks. Missing, malformed or challenge responses fail closed; other navigation failures are not ignored. This does not reload the page or retry the request. Analysis failures retain a bounded error code without provider bodies or credentials, and keep the item pending for a later bounded round.

Schema1 migration first validates input identities/FKs, makes a mode-0600 SQLite backup beside the private database, then transactionally copies all facts, observations, old decisions, quotes, run/expiry values and original notification payload/status. Mixed legacy purchase history belongs to a disabled `legacy-purchase-review`; only explicit current-task IDs create new task relationships. No old writer remains. Failed migration rolls back and unknown schemas fail closed. Stop the wrapper/timer before restoring a backup; preserve both files and delivery receipts. Restoring an old format requires running its pinned old CLI, not the current CLI against guessed tables.

Notifications are independent outbox records. Sender return 0 acknowledges delivery, 1 proves preflight failed and permits retry, and ambiguous errors/timeouts become `uncertain`; interrupted claims are uncertain as well. Old facts/criteria events become `superseded`. Expiry emits one final summary without more browsing/AI. `reconcile-send EVENT --result sent|retry` only resolves an uncertain event after operator verification; it does not repeat analysis. Exactly-once delivery across a network boundary is not promised.

Optional `collection_policy` adds suitable candidates to the platform's favorites: `enabled` defaults false, `max_per_run` defaults 1 (maximum 3), and enabling requires an owner-confirmed numeric `expected_account_id`. This is explicit account-write authority, not permission to contact sellers or buy. Only an active live task's current candidate with matching criteria, evaluator and item revision qualifies; prepare, reserved/rejected items and stale judgments cannot write. Detail/timeout budgets include collection verification, with a reserved detail slot. The adapter checks the page's normal login-user response and precise detail identity before using only the unique add control. It never clicks an already-saved control. Account mismatch, missing/ambiguous controls or platform boundaries fail closed.

Favorite prices come only from the card's current-price node, never all currency amounts in its title/discount/original-price text. The reader waits up to ten seconds for initial cards, then scrolls naturally at most 48 times; it stops when all requested identities appear or the bottom remains stable across three waits. A blank DOM fails rather than claiming an empty collection. Only watched cards' prices are read. Missing or conflicting nodes retain per-item coverage gaps while healthy cards and search continue. Watch recovery gets the existing detail budget first, without reserving unused collection slots; cached watch details can still feed AI at the detail limit. A missing favorite is not proof that a listing is offline: detail confirmation can resolve its coverage gap. Failures consume budget and partial rounds rotate. Unresolved prices/status remain explicitly partial. A changed list price marks status unconfirmed until detail verification, so its price notice waits. Normal page detail traffic's explicit status labels populate the existing `availability` snapshot field: sold/offline listings cannot generate candidate/price notices or be automatically collected, and unknown status cannot authorize a collection write. Status and configuration changes invalidate old assessments through the existing fingerprint; old facts/quotes/assessments are retained without a schema migration. Login/challenge failures still stop capture rather than degrade silently.

Existing SQLite `meta` stores action receipts keyed by account/item, shared across tasks; no schema migration or guessed backfill is needed. Intent is committed before clicking. A verified result deduplicates future attempts and adds the task relationship to daily watch reads. Interrupted/uncertain attempts can only read and reconcile the state next round; a still-unsaved uncertain result is retained as unconfirmed, never blindly clicked again. Receipts record actions, not a second authority for actual platform state. Favorites mean worth further verification, not proof of reliability. All real IDs/account identity/criteria remain private.

Login/challenge/rate-limit evidence blocks future capture globally. Recover the same account manually, then explicitly `--monitor TASK unblock`; no rotation/bypass. Routine API/schema failures remain recorded failures, distinct from true empty results. Independent health checks must monitor the timer and last successful **live** run; OnFailure alone cannot detect a timer that never fires.

`runtime.ai.transport` explicitly selects `claude-cli` or the backward-compatible default `chat-completions`; unknown transports fail closed and neither falls back to another provider. Cubi uses its existing `claude-glm` launcher, with `launcher`, `model` and `timeout` supplied by the private runtime profile. The launcher alone loads GLM credentials. Each invocation has an isolated temporary cwd/environment, no tools/MCP/browser/session persistence, one turn, low effort, a configured output-token limit, a 120-second default timeout and the existing CLI USD 0.20 budget guard. Timeout or cancellation terminates the invocation's process group. Stream JSON binds the assistant's actual provider model separately from Claude's client-profile usage accounting; only scalar usage and model identities are retained in `ai_last_receipt`. CLI accounting is not proof of cash billing. Per-monitor call limits bound subscription use. Invalid/incomplete output keeps items pending.

For `chat-completions`, host API keys come from environment, never a config file. Its runtime profile supplies an HTTPS endpoint, configured model, explicit verified price ceilings and a cumulative USD cap (max 3). UTF-8 byte/input and output-token bounds reserve cost before each request, including ambiguous failures; no refunds/retries assume success. Verify provider pricing/eligibility before using this channel. Historical Cubi trial runs used ordinary DeepSeek; their receipts and cost reservations remain in the ledger, and are not rewritten by the GLM switch.

Scheduled `run` retains per-item partial coverage but returns success for a single partial round.
Partial runs never advance the successful-live heartbeat; the host's existing 36-hour
sentinel escalates persistent incompleteness. Explicit `scan`/prepare still returns nonzero
for partial results. Failed/blocked/degraded rounds and uncertain/retry delivery always
remain nonzero, including when another task completes successfully.

Focused checks, without upstream Web fixtures:

```
PYTHONDONTWRITEBYTECODE=1 python3 -m pytest tests/cubi --confcutdir=tests/cubi -q -p no:cacheprovider -o addopts='--tb=short'
```

Only synthetic test inputs/examples are public. Personal comparisons, real item snapshots, negotiation prices, browser evidence, databases and migration backups belong in ignored/private storage. CLI summaries omit API errors and credentials. Cubi owns its wrapper, systemd units, chosen private configuration and existing Telegram sender; this repository owns the core.
